# PMLSM MIL Model Notes

## Stable Baseline

The main development model is:

```text
PMLSM_MIL_ControlCore_Sim.slx
```

The top level is organized into four functional subsystems:

- `Startup_And_Commands`: MIL modes, startup sequencing, test commands, and
  fault-injection commands.
- `Control_Core`: the `PMLSM_ControlCore_Block` model reference plus command
  and feedback adapters.
- `Power_Plant_Feedback`: inverter, dq plant, sensors, feedback selection,
  and current reconstruction.
- `MIL_Logging`: all `logsout` and To Workspace collection.

Cross-subsystem signals are grouped into `Startup_Bus`, `ControlCore_Bus`,
and `Plant_Bus`. The buses pass through subsystem Inport/Outport interfaces.
Goto/From tags are local to the subsystem that owns them and therefore display
with square brackets. No scoped tags, global tags, or `Goto Tag Visibility`
blocks remain.

The top level uses three local bus tags: `[Bus_Startup]`,
`[Bus_ControlCore]`, and `[Bus_Plant]`. Inside each subsystem, local signal
tags are kept short unless a signal has multiple possible sources.

The current routing audit reports:

- `PMLSM_MIL_ControlCore_Sim`: 121 local Goto blocks, zero scoped/global.
- `PMLSM_ControlCore_Block`: 67 local Goto blocks, zero scoped/global.
- The MIL library and two frozen models contain no Goto blocks.

The frozen Full_Startup_MIL baseline is:

```text
PMLSM_MIL_ControlCore_Sim_FullStartup_OK.slx
```

The frozen file was copied before the parameter-layer and
`Plant_Input_Mode` work. Its SHA256 matched the main model at the time of
freezing. The frozen model is not regenerated by the build scripts.

The original code-generation and hardware model remains:

```text
PMSLM_Close_Loop_MBDL4.slx
```

## Simulation Modes

- `MIL_Mode = 1`: `Iq_Test_Debug`.
- `MIL_Mode = 2`: natural startup through
  `Angle_Init -> Init_Done -> Close_Loop_EN -> speed loop`.
- `Plant_Input_Mode = 1`: `vd_cmd/vq_cmd` directly drive the dq plant
  through the inverter enable gate. This is the default regression path.
- `Plant_Input_Mode = 2`: `duty_a/duty_b/duty_c` are converted from ePWM
  compare counts using `duty_ratio = 1 - CMPA/PWM_Period`, reconstructed
  to three-phase average voltage, transformed to dq, and then applied to
  the plant. This legacy polarity path is kept because the code-generation
  model and real hardware have already driven the motor successfully.

All models use fixed-step discrete simulation with `FixedStep = 1e-4 s`.

## Accurate PWM Update Timing Option

`Power_Plant_Feedback/Inverter_Model/PWM_Update_Delay` retains the legacy
`MIL_PWM_Update_Delay_Mode = 0/1/2` path for existing 100 us regressions.
An optional event-accurate path is selected with:

```matlab
MIL_PWM_Update_Delay_Accurate_Enable = 1;
MIL_PWM_Delay_Substep_s = 5e-5;
MIL_Current_Control_Ts_s = 1e-4;
```

The accurate path samples and holds the controller duty at 100 us. Mode 1
then applies one 50 us Unit Delay, while mode 2 applies two cascaded 50 us
Unit Delays. Unlike the legacy half-delay path, it does not average current
and previous duty commands.

Accurate timing runs must also use a 50 us fixed solver/plant step. When the
MIL command layer runs at that step, set `MIL_Ts_s = 5e-5`. Preserve a 5 ms
position-difference speed window with `PMLSM_sensor_delay_samples = 100` and
`PMLSM_Ts_s = 5e-5`.

Verification script:

```matlab
verify_AUM3S4_accurate_pwm_update_delay
```

It directly compares the held duty command and delayed duty output. The
verified lags are exactly one 50 us substep for mode 1 and two substeps for
mode 2, with zero sample-alignment error.

## Half-Sample Compensated DPICC

`Current_Control_Mode = 4` retains the mode 3 incremental DPICC and adds the
50 us PWM-update prediction term. The controller still executes only on the
100 us PRD task. It stores two successive limited dq voltages, so
`delta_U_prev` is formed from actual limiter outputs rather than raw voltage
requests. A first-active-tick detector zeros the current and voltage increment
history terms when the mode is enabled after alignment.

Run:

```matlab
run_AUM3S4_dpicc_half_sample_comp
```

The stationary test uses `MIL_Mode = 4`, which reuses the mode 1 iq profile
but waits for `Close_Loop_EN`. Its 50 us plant log verifies that pending voltage
updates occur only at PRD and active voltage updates occur only at ZERO. No
half-sample voltage averaging is used.

## Parameter Layers

Controller and code-generation parameters:

```text
init_PMLSM_control_params.m
```

This script calls `PMSLM_Init_Params_MBDL4.m`, which remains the single
source of truth for controller values. No PI values were changed.

MIL plant and sensor parameters:

```text
init_PMLSM_plant_params.m
```

These use a `PMLSM_*` prefix and are referenced only by
`PMLSM_Plant_Model`, `Inverter_Model`, and `Sensor_Model`. Existing values
were preserved. Plant-only mass, force constant, friction, sensor, and
electrical parameters do not become dependencies of the original
code-generation model.

`PMLSM_MIL_Library_Sim.slx` is currently an independent open-loop component
test harness. Its top-level constants are used only when that model is run by
itself. The main MIL build copies `Inverter_Model`, `PMLSM_Plant_Model`, and
`Sensor_Model` into `PMLSM_MIL_ControlCore_Sim`; these copies are connected to
the ControlCore buses but are not live Simulink library links.

The plant phase currents are generated explicitly through inverse Park and
inverse Clarke transforms:

```text
id/iq -> i_alpha/i_beta -> ia/ib/ic
```

The plant's `ic` output no longer uses `-(ia+ib)`. The main MIL feedback path
now uses independent three-phase sampling:

```text
ia -> ia_meas
ib -> ib_meas
ic -> ic_meas
```

`PMLSM_current_feedback_mode = 3` marks this MIL mode. The previous MIL-side
`ic = -ia - ib` reconstruction block is no longer used in the main feedback
path.

The speed measurement delay is:

```text
PMLSM_sensor_delay_samples = 50
v_meas_mmps = (x(k)-x(k-50))/(50*PMLSM_Ts_s)
```

MIL startup and fault-test parameters:

```text
init_PMLSM_mil_test_params.m
```

These use a `MIL_*` prefix and are referenced only by the MIL sequencer,
plant-input selection, and test scripts.

`init_PMLSM_MIL_params.m` remains as a compatibility entry point that loads
all three layers.

## Full Startup Regression

Run:

```matlab
run_PMLSM_MIL_full_startup_check
```

Verified results:

- `Init_Done` reaches 1 naturally.
- `Close_Loop_EN` reaches 1 after the configured delay.
- `fault_latch` remains 0 during the nominal sequence.
- `v_ref_safe` reaches `+5 mm/s` and `-5 mm/s`.
- `iq_ref` becomes nonzero after the speed command.
- Mean speed during the positive command is approximately `+5.55 mm/s`.
- Mean speed during the negative command is approximately `-5.58 mm/s`.

`Plant_Input_Mode = 1` was compared against the frozen model. All selected
signals were identical except an `iq` difference of approximately
`1.08e-19`, which is numerical roundoff.

- `x_mm`: approximately `1.73e-5 mm`.
- `iq_ref`: approximately `5.80e-4 A`.

## Fault Injection

Run:

```matlab
run_PMLSM_MIL_fault_injection_tests
```

All eight tests pass after the hardware fault update:

- `fault_i = 1`: PWM enable is removed and `fault_latch` is set.
- `fault_u = 1`: PWM enable is removed and `fault_latch` is set.
- `enable_cmd = 0`: PWM enable is removed and `fault_latch` is not set.
- Soft-limit position: outward speed is blocked, hard fault is not latched,
  and the retreat direction remains available.
- Overspeed injection: `fault_latch` is set and `v_ref_safe` is forced to 0.
- Speed reference step to 0: command and safe reference return to 0.
- Load-force step: the disturbance produces a measurable speed response
  without changing plant parameters.
- DC-bus drop: mode 2 reflects the reduced bus voltage in reconstructed
  plant voltage.

Current interface boundary:

- `fault_i` is treated as drive hardware over-current.
- `fault_u` is treated as drive hardware over-voltage.
- `fault_i || fault_u` is latched into the MIL ControlCore `fault_latch`
  path and also removes PWM enable.
- `enable_cmd = 0` removes PWM enable but does not set `fault_latch`.
- Travel soft/hard limits and overspeed behavior remain in the original
  `Travel_Safety_Manager` logic.

Per-test logs and plots are saved under:

```text
data/mil_logs/fault_injection
```

## Hardware ePWM and Inverter Polarity

PWM polarity is not a current blocking item. The current code-generation model
and real F28335 hardware have already driven the motor successfully in previous
hardware runs, so the MIL inverter polarity should remain consistent with that
already-running path.

Confirmed F28335 ePWM facts:

- TBCLK: `150 MHz`.
- PWM frequency: `10 kHz`.
- PWM period: `7500` counts.
- Count mode: Up-Down.
- ePWMA action: CAU Clear, CAD Set, ZERO/PERIOD Do nothing.
- Deadband polarity: Active high complementary.
- RED/FED: `150` counts = `1 us`.

The current MIL `Plant_Input_Mode = 2` average inverter still uses:

```text
duty_ratio = 1 - CMPA/PMLSM_pwm_period_counts
```

This legacy path is intentionally not modified now. Do not change
`Inverter_Model` polarity only from standalone ePWM theoretical analysis. Only
revisit the conversion if a future oscilloscope test, hardware current
response, or motor-force direction test shows inconsistency between MIL and the
real inverter output.

The diagnostic script remains available:

```matlab
check_pwm_polarity_mapping
```

It is retained for documentation and diagnosis, not as a current action item.

## Hardware Regression Preparation

Items still requiring real hardware or Maxwell validation:

- Confirm DC-bus measurement scaling and undervoltage behavior.
- Identify actual moving mass, force constant, viscous friction, and
  Coulomb friction.
- Confirm `Rs`, `Ld`, `Lq`, and flux linkage against measurement or Maxwell.
- Validate encoder polarity, `tau_e = 30 mm`, and electrical-angle offset.
- Validate current-sensor gains, offsets, delay, and noise.
- Confirm soft/hard travel limits and overspeed thresholds on the machine.
- Validate that hardware `fault_i/fault_u` latch behavior matches the updated
  MIL protection path.
- Validate startup alignment current and hold duration for thermal and
  mechanical safety.
- Repeat the same command sequence in HIL/Maxwell and then at reduced
  current and speed on hardware.
